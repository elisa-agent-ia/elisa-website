Deployment & models

Your servers or ours. Your model, always.

The same software everywhere: one server, a Kubernetes cluster, or a dedicated instance we run for you. Pick the model provider, or host the model yourself. It can run end to end without a US provider: your servers or an EU host, an EU model or your own.

Where it runs

Three ways to run it, one product.

For a first installation

Single server

One Linux server in your cloud or data centre; air-gapped installs included (upgrades through a mirror of the Elisa registry). Docker Compose and one command-line tool, elisactl, to install, upgrade, back up and roll back. Plan 4 CPUs and 8 GB of memory for a small team.

For larger companies

Kubernetes

A Helm chart with several replicas, worker pods, a migration job, non-root read-only pods, and skill sandboxes in pods of their own, isolated by gVisor† where your cluster offers it. Works with GitOps tools such as Argo CD and Flux: our hosted instances are run that way.

For companies that want no infrastructure

Hosted by us

We run a dedicated installation for you, with your identity provider and your model. We handle upgrades and backups. At the end of the contract we hand over your data: database, files, the vault key and the store key. Region: France, with OVHcloud.

All three run the same images, the same code and the same licence rules. Only who operates them changes.

What stays yours

Upgrades never overwrite what you own.

Replaced at each version

We ship

The server, the agent runtime, the web app, the sandboxes, the egress proxy, the bundled skill packs and the installer, as versioned images.

Never overwritten

You own

Your settings, your secrets, your licence, your governance repository (skills, knowledge, policies) and your data (conversations, files, approvals, audit), outside the images. Upgrades migrate your database after backing it up; they never overwrite the rest.

Models

Use the model you trust, or several.

  • Supported providers: OpenAI, Azure OpenAI†, Anthropic†, Amazon Bedrock†, Google Vertex AI† (Gemini), and any server that speaks the OpenAI API: vLLM, Ollama, LiteLLM, Mistral, OpenRouter, DeepSeek and others.
  • Models you host: point Elisa at your own OpenAI-compatible server, for example an open-weight model on your GPUs. Prompts then stay in your network.
  • Aliases, not hard-coded names: you name aliases (for example default, large, fast) and map each to a provider and a model, with a fallback. Changing a model is a settings change, not a migration.
  • Per role: roles say which aliases people may use; people pick the model per conversation within that list.
  • Tested models, published: we publish our real-model test results and the script to test yours, and we test your chosen model with you during setup.
  • Attachments: images, PDF, Office documents, and audio through a transcription endpoint.
ELISA_MODELS__DEFAULT__PROVIDER=openai
ELISA_MODELS__DEFAULT__BASE_URL=https://llm.internal.example/v1
ELISA_MODELS__DEFAULT__MODEL=gpt-oss-120b

Data residency

Your data stays where you put it.

  • Database: PostgreSQL (SQLite for trials). Files: a local or shared volume, or object storage (S3-compatible, Google Cloud Storage†, Azure Blob Storage†).
  • Encrypted at rest by default: conversations in the database and files on the volume or in the bucket are ciphertext under a store key that stays on your servers. Keep an offline copy of that key apart from your backups, like any master key.
  • Self-hosted: everything stays in your network, except the outbound paths you configure (model provider, web search, the hosts your skills declare; the full list is on the Security page).
  • Hosted by us: in France, with OVHcloud, dedicated instance, under a data processing agreement.
  • Air-gapped: load the images offline and run with a model you host; upgrades come from a mirror of the Elisa registry inside your network.

Operations

Upgrades back up first and roll back by themselves.

  • elisactl upgrade shows the upgrade notes, takes a backup, migrates, checks health, and rolls back by itself if anything fails: the database returns to its state before the upgrade.
  • elisactl backup covers the database, the vault and the encrypted conversation files (uploads too, with local file storage). Archives hold ciphertext and the ids of the keys, never a key; restores use the store key.
  • Choose how you follow releases: a fixed version, fixes only, or the latest stable release. Elisa upgrades when you decide.
  • Within a release line, settings and the public API are only added to, never removed (our policy).
  • Prometheus metrics and OpenTelemetry traces†, without message content.
$ elisactl upgrade
current version: 0.1.6
==> Backing up to backups/elisa-2026-11-14T10-02.tar.gz
==> Pulling images
==> Running database migrations
==> Checking health
warning: rolling back to 0.1.6

Operations

Run what you want. We run the rest.

Servers, model, operations, skills: we can take care of all of it, so your teams focus on using Elisa and the value it brings. For each part, you choose: you, or us.

Servers

Us: a dedicated instance hosted in the EU, monitored and backed up by us. You: one Linux server is enough to start (4 CPUs, 8 GB), about 1.5 GB of memory per active sandbox; we size it with you.

Model

Us: we provide model access and size it for you. You: the provider of your choice, or a model you host. Either way, Elisa keeps prompts small (about 800 tokens for a 100-skill catalogue in our benchmark¹) and compresses large outputs, so the bill stays low.

Operations

Us: upgrades, backups, monitoring and key rotation, with nothing to do on your side. You: one command per operation, about 2 to 4 hours a month.

Skills

Us: your project manager gathers your processes and tools; we write the skills and keep them up to date. You: your teams write them, helped by the Claude Code skills we provide; a simple skill typically takes 1 to 3 days.

Licence

A licence that never phones home.

  • A signed file, checked offline. The running software never contacts us. It works in air-gapped networks.
  • Above your licensed number of people, administrators see a warning. Nobody is locked out.
  • After expiry, 30 days of grace with everything working. Then Elisa becomes read-only: people can still sign in and read their data.
  • Your skills are yours: they live in your Git repository; at the end of the contract, your skills and knowledge are handed back to you and you can reuse them freely.
  • If we stop trading: your licence becomes perpetual for the version you run. You keep the right to run it on your own servers, indefinitely.

Requirements

What you need to start.

Single server

  • Linux with Docker Engine 28+ and Compose 2.20+, openssl
  • 4 CPUs, 8 GB memory for a small team, plus about 1.5 GB per sandbox running at once
  • A DNS name and a TLS reverse proxy
  • An OpenID Connect client from your identity provider
  • A model endpoint and key
  • Registry credentials and a licence file (from us; for evaluation, Elisa also runs for up to 5 people, free for 30 days)

Kubernetes

  • A cluster with an ingress controller
  • Your PostgreSQL
  • For more than one replica, a shared volume (ReadWriteMany) or S3-compatible object storage
  • Nodes for the sandboxes (gVisor recommended where available), with memory for each sandbox's in-memory copy of its files (about 0.8 GB by default, on top of its own limit)
  • The same identity, model and licence items

Sizing figures are estimates. We size with you during the pilot.

Deployment FAQ

Can it run in an air-gapped network?

Yes. It installs on a single server in an air-gapped network, with a model you host. Upgrades come from your Elisa registry or a mirror of it. The licence is checked offline; the running software never contacts us. Skills reach only the hosts you allow.

Is the hosted version dedicated to our company?

Yes. It is a dedicated installation for your company only.

Can we move from hosted to self-hosted, or back?

Yes: same images and data format. We hand over the database backup, the files, the vault key and the store key, and you restore them.

Do you support SAML or SCIM?

Both are coming soon. Meanwhile, Keycloak can bridge to a SAML identity provider†. Today Elisa signs in with OpenID Connect, and directory sync with Microsoft Graph†, Google Directory† or Keycloak† removes access at the next sync (hourly by default) when people leave.

Which Git hosts?

GitLab and GitHub, or a local repository to start.

Do we need GPUs?

Only if you host the model yourself.
